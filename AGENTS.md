# kyora

## Public repository

This repository is public. Never reference private repositories, infrastructure, host names, internal URLs, customers or events in code, docs, commits or PR text. Keep the copy about the runtime itself.

## Docs

- Don't add or edit docs, READMEs, guides or comments to describe a fix or a change's history. The PR body carries that.
- Touch user docs only when public API, CLI or user-visible behaviour changes, and then minimally. Design docs in `docs/` change when the design does.
- No process, status, planning or agent-loop documents in the repo: operating guides, running logs, plans, personal paths or environments.

## Copy

No em dashes or en dashes anywhere: docs, comments, commit messages and PR text. Use commas, colons, periods or parentheses.

## Titles

PR and commit titles use scoped conventional commits: `type(scope): summary`. Scope is the affected crate or area: `core`, `providers`, `tools`, `mcp`, `protocol`, `cli`, `tui`, or an area (`docs`, `ci`, `deps`). Keep the summary concise.

Examples: `feat(core): child agents with ownership, limits and ordered shutdown`, `fix(tools): accept trusted spellings of the workspace root`, `ci(deps): bump actions/checkout`.

## PR style

PR bodies follow this template:

```
TL;DR:
<human (!) written tl;dr of the pr>

Before/After:
<only for visual changes: before and after screenshots>

Repro:
<only for bug fixes: the failing test, or the steps that reproduce the issue>

Summary:
<concise bullets, gen'd by agent>

Test plan:
<check-boxes the author must fulfill before pinging for review>
```

Section rules:

- **TL;DR**: written by a human, always. Agents must leave it empty and never fill it in.
- **Before/After**: include only when the PR makes visual changes (TUI, CLI output). Upload before and after screenshots following the review artifact rules below. Omit the section otherwise.
- **Repro**: for bug fixes, name the regression test that fails without the fix, or give the steps that reproduce the issue. Omit the section otherwise.
- **Summary**: concise bullets describing what changed, generated by the agent. What changed, not how.
- **Test plan**: GitHub check-boxes (`- [ ]`). The author must fulfill every box before pinging for review.

## PR review

- Every PR gets two reviews with the same standing: kyora review (the `kyora[bot]` summary and the `kyora review` check), and a deep review by Codex `gpt-6.1-sol` at effort `max`.
- After opening a PR, wait for both. Read every finding, assess whether it is valid, and tell the user what you propose to fix or dismiss. Fix valid findings within the authorized scope and run the relevant checks.
- Reply to each review thread with the fix and validation, or explain why the finding does not apply. Resolve threads only once addressed.
- After pushing fixes, get a fresh review from both:
  - comment `@kyora-review review` unless a kyora review of the new commit already started;
  - rerun the Codex review on the new commits.
  - Repeat until there are no actionable findings.
- Verify that each review covers the latest commit; the kyora summary footer names the commit it reviewed. Resolving a thread does not replace a fresh review. If a review is unavailable or still pending, say so explicitly and do not present the PR as cleared.

## Review artifacts

Put review screenshots, repro files, recordings and logs in the PR, never in git. Keep test fixtures. Use GitHub CLI **v2.101.0+** for image and video attachments:

```bash
gh pr comment "$PR_NUMBER" --attach /tmp/before.png --attach /tmp/after.png
```

Attach other files through GitHub's web UI. If uploading fails, report it; do not commit the files as a workaround.
